# Proposed Range D: artifact provenance and configuration

**Status:** design only. No production CI, repository, registry, deployment, or credentials are connected. Synthetic services would represent repository metadata, build history, artifact records, release policy, and configuration state. This family adds provenance graphs and coordinated configuration relationships, not another stale-role approval case.

| Archetype | Public workflow and property | Independent verification and controls | Candidate factors and ambiguity |
| --- | --- | --- | --- |
| D1 Release artifact provenance | Users inspect the declared source → build → artifact → release lineage. A promoted artifact must have a consistent authorized lineage. | Reconcile immutable synthetic lineage records and generation-bound observations. Controls include valid rebuilds, alternate branches, and mismatched lineage. | D2 graph hops, D5 service joins, D7 independent lineage observations; multiple legitimate builds must be allowed. |
| D2 Environment promotion policy | Users inspect proposed promotion records and environment policy. Completed promotions must satisfy the declared policy. | Compare policy revision, promotion record, and final environment state. Controls include permitted exceptions and disallowed transitions. | D3 policy predicates, D4 ordering, D7 before/after evidence; policy version changes need clear timing. |
| D3 Configuration data boundaries | Users inspect synthetic configuration views with different declared visibility. Restricted values must remain within their authorized surfaces. | Verify identity, field classification, response generation, and intended public projection. Controls include public metadata and restricted synthetic fields. | D3 scopes, D6 similar public/private fields, D7 identity-bound observations. |
| D4 Rollback and dependency consistency | Users inspect a synthetic rollback across linked release and configuration records. Final states must respect declared dependencies. | Reconcile the dependency graph and authoritative postcondition records. Controls include valid partial states during a documented transition and invalid final states. | D2 dependency edges, D4 phases, D5 cross-service state, D7 ordered observations. |

Each future task needs a versioned template, vulnerable/patched behavior defined by a checkable invariant, a normal public observation path, a private verifier, positive and negative controls, and a split group that keeps semantically equivalent variants together. The design does not propose live deployments, real secrets, external integrations, or operational attack steps.
